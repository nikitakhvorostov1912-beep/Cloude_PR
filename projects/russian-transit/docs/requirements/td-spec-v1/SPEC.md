# SPEC — Интеграция ТД Владимира в 1С (v1)

> Снапшот архитектуры на 2026-04-23. Финальная версия, выверенная на живых данных MCP + реальном CSV от Владимира.

## Задача

В 1С нет механизма загрузки транзитных деклараций (ТД). API Сигмы отдаёт только ДДП (договор-поручительство) — клиентов, которым мы дали обеспечение. ТД клиентов, которым мы только возили декларацию (обеспечение у другого брокера), через API невидимы. Результат:
- 0 документов `ТолькоТД` в базе (хотя такие клиенты есть — Владимир видит их в своём ЭТД-журнале)
- Строки ТЧ `ДанныеДокументов` не содержат Рег.№ТД, Подразделение, КолКодовТНВЭД → Schema 4 не может считать штраф за коды
- 99% строк имеют пустой `ТипУчета` → `исРасчет` уходит в fallback → почти всё считается как Комплекс

## Решение — 2 источника данных в 1 документ

```
┌─────────────────────┐          ┌─────────────────────┐
│ API Сигмы           │          │ CSV Владимира       │
│ ДДП (поручительства)│          │ Сами ТД (декларации)│
└──────────┬──────────┘          └──────────┬──────────┘
           │ EPF APIСигма                   │ Обработка.ЗагрузкаРееструТД (NEW)
           ▼                                ▼
     ┌──────────────────────────────────────────┐
     │ Документ.ОперацияПоПоручительству        │
     │   ВидОперации = ДДПАвто | ТДФайл         │
     │   ТЧ ДанныеДокументов (per-row ТипУчета) │
     └──────────────────────────────────────────┘
                        │
                        ▼ АРМ → Пересобрать → Рассчитать
                  ┌──────────────┐
                  │ исРасчет     │ → правильная сумма per-row
                  └──────────────┘
```

## Ключевые решения

### 1. Один тип документа, не два

`ОперацияПоПоручительству` используется для всех трёх режимов (Комплекс / ТолькоТД / ТолькоОбеспечение). Различаются через:
- Реквизит шапки `ВидОперации` (2 значения: `ДДПАвто` 🌐 или `ТДФайл` 📑)
- Per-row реквизит `ТЧ ДанныеДокументов.ТипУчета` (3 значения перечисления `ТипыУчетаКлиентов`)

**Почему:** `исРасчет` уже умеет считать per-row, АРМ работает единым реестром, миграция минимальна.

### 2. Matcher — прямое правило по колонке CSV «Номер ДДП ТД»

В CSV Владимира колонка #33 «Номер ДДП ТД» содержит прямую связь ТД↔ДДП (формат `10000000/270226/0119685` совпадает с `НомерГТД` в ТЧ 1С). Эвристики не нужны:

```
Для каждой строки CSV:
  ЕСЛИ «Номер ДДП ТД» заполнен (478/485 = 98.6%):
     SELECT Документ из ОПП ГДЕ ДанныеДокументов.НомерГТД = csv.НомерДДПТД
     → строка.ТипУчета = Комплекс
     → дозалить: РегНомерТД, Подразделение, ТС, Декларант,
                 ДатаВыпуска, КоличествоКодовТНВЭД
  ИНАЧЕ (7/485 = 1.4%):
     CREATE Новый Документ ОПП
       ВидОперации = ТДФайл, СуммаОбеспечения = 0
     ADD строку в ТЧ ДанныеДокументов
       ТипУчета = ТолькоТД
       НомерГТД = csv.РегНомерТД

После прохода всех строк CSV:
  Существующие строки ДД, у которых НомерГТД не встретился в CSV
  → ТипУчета = ТолькоОбеспечение
```

### 3. Подразделение — справочный атрибут, не определитель типа

Подтверждено на реальных данных:
| Подразделение | ТД с ДДП | ТД без ДДП |
|---------------|----------|------------|
| Центральный офис | 345 | 7 |
| Трейд Солюшнс | **132 (все)** | 0 |
| ТАРГА | 0 | 1 |

«Трейд Солюшнс» — наше внутреннее подразделение РТ, а не признак ТолькоТД. Все три подразделения могут вести любой тип учёта. Подразделение сохраняется как справочный атрибут для группировки в отчётах.

### 4. Schema 4 — используем готовое число из CSV

Колонка #45 «Количество уникальных кодов ТН ВЭД» в CSV уже содержит число (15, 26, 3, ...). Не нужно считать коды самим — штраф Schema 4 считается по формуле `max(0, cnt-5) * 0.2 * цена`.

### 5. Миграция существующих 1572 документов

Одна команда при установке расширения:
```sql
UPDATE Документ.ОперацияПоПоручительству
SET ВидОперации = &ДДПАвто
WHERE ВидОперации IS NULL
```
Корректно, так как все существующие документы пришли через «Чтение деклараций» / EPF APIСигма (ТолькоТД документов в базе 0).

## Что НЕ делаем

| НЕ делаем | Причина |
|-----------|---------|
| Отдельный `Документ.ОперацияПоТД` | Один тип проще, исРасчет уже работает per-row |
| Регистр «ВыпущенныеТД» | Избыточно, данные ТД живут в ТЧ нужного документа |
| 3-шаговый matcher (ТС+Декларант+Дата) | В CSV есть прямая связь ТД↔ДДП |
| Классификация по Подразделению | Подразделение = наш отдел РТ, не тип клиента |
| Переписывать `исРасчет` | Уже корректно работает (стр. 41-48, 64, 924) |
| Трогать АРМ / ЧтениеДеклараций | Ортогональные задачи |
| Считать коды ТНВЭД самим | В CSV готовое число (col #45) |
| Прямую интеграцию Sigma PISrv | После инцидента 2026-04-08 сервер под ограничениями |

## Пользовательские сценарии

### Бухгалтер (никаких изменений)
Открывает АРМ → выбирает период → «Пересобрать» → «Рассчитать» → получает правильную сумму.

### Владимир, день 1 (массовая первая загрузка)
1. Экспортирует ЭТД-журнал за 4-6 недель (~2000 строк)
2. Обработка «Загрузка реестра ТД» → 3 вкладки:
   - ✅ Комплекс (обогащение существующих) — ~1950
   - ➕ Новые ТолькоТД — ~30-50
   - ⚠ Без пары → ТолькоОбесп. — ~50-100
3. Проверяет «Без пары», применяет
4. Результат: per-row ТипУчета заполнен у >80% строк, в базе появились документы ТолькоТД (было 0)

### Владимир, день N (рутина ~3 минуты)
1. Экспортирует ЭТД за сутки (~80 строк)
2. Обработка раскладывает → обычно 0-3 ТолькоТД, остальное Комплекс
3. Применяет, бухгалтер жмёт Рассчитать

## Журнал документов — визуальное различение

В форме списка `ОперацияПоПоручительству`:
- **Реквизит шапки** `ВидОперации` с двумя значениями
- **Фильтр-чипы** сверху: `Все | 🌐 ДДП — автозагрузка | 📑 ТД — ручная загрузка`
- **Цветная полоса слева** (условное оформление): синий = ДДП авто, зелёный = ТД файл
- **Колонка «Вид операции»** с иконкой

При ручном создании документа `ВидОперации` ставится автоматически по `СуммаОбеспечения` (>0 → ДДПАвто, =0 → ТДФайл), пользователь может переопределить.
