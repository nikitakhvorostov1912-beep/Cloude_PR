§1 Что такое ТД глазами Владимира

ТД (транзитная декларация) — это реальный таможенный документ. Для Владимира это единица учёта обеспечения: один ТД = один «договор поручительства» с набором кодов ТН ВЭД и собственным состоянием.

💰 В расчёте

Каждая активная ТД даёт вклад в итоговую цену обеспечения по формуле:

// Per-ТД Schema 4
ЦенаПоТД =
    Цена × 1             // базовая
  + max(0, uniqКодов − 5)
      × 0.2 × Цена;       // штраф за коды >5

Итого = Σ ЦенаПоТД
       + Σ ОплатаУслуг
       + Σ ДопУслуги;

Ключевое правило: штраф считается независимо для каждой ТД, а не по всему документу сразу (сейчас это Schema 4 bug).

§2 Путь ТД: Сигма → 1С

Одна ТД проходит 4 стадии. Первые 2 — автоматические, последние 2 — ручные (пока клиент не пришлёт точные правила группировки).

1. Источник
Сигма API
HTTP GET с participantcode в query, получаем CSV-поток (или XML). Каждая строка = один CMR / одна ТД.
2. Загрузка
EPF «APIСигма»
Обработка парсит CSV, пишет в ТЧ КодыCMR формы. Поля [38] → НомераCMR, [76] → НомерЭТД (П-04 fix 2026-04-07).
3. Перенос в документ
ОперацияПоПоручительству
Оператор выбирает нужные строки из EPF и переносит их в ТЧ КодыCMR документа. Параллельно заполняет ДанныеДокументов (1 строка ДД = 1 ТД).
4. Расчёт
исРасчет.ОбновитьЦены
При ПередЗаписью пересчитывается цена обеспечения по каждой ТД отдельно (Schema 4 per-ТД).

⚠ Узкое место: связь кода ↔ ТД

Сейчас в ТЧ КодыCMR нет прямого FK на строку ДД. Связь строится по совпадению НомерДополнения (код) ↔ НомерГТД (ДД). Если оператор неправильно привязал — коды «утекут» в соседнюю ТД.

В Phase 1.5 решается ежедневным реестром выпущенных ТД от Владимира (CSV): если № ТД из ДДП совпадает с РегистрационныйНомер ТД в реестре — это Комплекс; если не совпадает — fallback по ТС + Декларант + Дата; если и это не дало — ТолькоОбеспечение.

§4 Три кейса учёта ТД (enum ТипыУчетаПоПоручительству)

Владимир различает три сценария. Тип учёта — per-row, т.е. один документ может смешивать разные кейсы в разных строках ДД.

🔵 Комплекс

ТипыУчетаПоПоручительству.Комплекс

Полный цикл: обеспечение + оформление ТД с кодами ТН ВЭД.

  • Базовая цена за ТД
  • + штраф за коды >5 (per-ТД)
  • + расстояние (если превышено)
  • + доп. услуги CMR

Самый частый случай. Требует все связанные ТЧ.

🟡 ТолькоОбеспечение

ТипыУчетаПоПоручительству.ТолькоОбеспечение

Клиент уже оформил ТД сам — нам нужно только обеспечение.

  • Базовая цена за ТД
  • + расстояние
  • — без штрафа за коды
  • — без доп. услуг

ТЧ КодыCMR может быть пустой.

🟣 ТолькоТД

ТипыУчетаПоПоручительству.ТолькоТД

Клиент пришёл за оформлением ТД без нашего обеспечения.

  • — без базовой цены обеспечения
  • Штраф за коды >5 (per-ТД)
  • Доп. услуги CMR

ТЧ ДополнительныеУслуги обязательна.

§5 Статусы ТД — какие идут в расчёт, какие нет

В перечислении СтатусыТранзита сейчас 13 значений. Нужно добавить 14-е: ТаможенныйДосмотр. Фильтр статусов применяется в функции ПостроитьДопускТД(Объект).

✓ДополнениеЗарегистрировано

✓ТоварВыпущен
✓ТранзитЗавершен
✓ТранзитЗавершенСОговорками
✓ДополнениеОтправлено
✗АннулированоСпециалистом
✗ВЗаключенииДополненияОтказано

⚠ Почему ТаможенныйДосмотр → ✗ исключить?

В случае таможенного досмотра ТД ещё не разрешён к транзиту, обеспечение не сработало → клиент не должен платить по этой ТД до получения окончательного статуса. Владимир: «на досмотре — не считаем, пусть доедет».

// CommonModules/исРасчет/Ext/Module.bsl — новая функция
Функция ПостроитьДопускТД(Объект) Экспорт
    Допуск = Новый Соответствие;
    ИсключаемыеСтатусы = Новый Массив;
    ИсключаемыеСтатусы.Добавить(Перечисления.СтатусыТранзита.АннулированоСпециалистом);
    ИсключаемыеСтатусы.Добавить(Перечисления.СтатусыТранзита.ВЗаключенииДополненияОтказано);
    ИсключаемыеСтатусы.Добавить(Перечисления.СтатусыТранзита.ОтказаноВПриемеДополнения);
    ИсключаемыеСтатусы.Добавить(Перечисления.СтатусыТранзита.ТоварНеВыпущен);
    ИсключаемыеСтатусы.Добавить(Перечисления.СтатусыТранзита.ТаможенныйДосмотр); // NEW

    Для Каждого СтрокаДД Из Объект.ДанныеДокументов Цикл
        Если ИсключаемыеСтатусы.Найти(СтрокаДД.СтатусТранзита) = Неопределено
           И Не ПустаяСтрока(СтрокаДД.НомерГТД) Тогда
            Допуск.Вставить(СтрокаДД.НомерГТД, СтрокаДД);
        КонецЕсли;
    КонецЦикла;
    Возврат Допуск;

§6 Как ТД влияет на расчёт — интерактивный калькулятор

Основное отличие: сейчас штраф считается на весь документ сразу (Schema 4 bug), а должен считаться per-ТД. Подвигайте ползунки — видно разницу.

❌ СЕЙЧАС (Schema 4 bug) WRONG

uniq_all = A + B − Dup
штраф = max(0, uniq_all − 5) × 0.2 × Цена (один раз)
base = Цена × КоличествоТД

✓ ВЛАДИМИР (Schema 4 правильная) RIGHT

Для каждой ТД отдельно:
штраф_i = max(0, uniq_i − 5) × 0.2 × Цена
base = Цена × КоличествоТД

Что меняется в коде

// CommonModules/исРасчет/Ext/Module.bsl

// ===== БЫЛО (bug): считаем уникальные по всему документу =====
Функция РассчитатьОформлениеТД(Объект, Цена) Экспорт
    Если Цена = 0 Тогда Возврат 0; КонецЕсли;
    Уник = Новый Соответствие;
    Для Каждого СтрокаКодов Из Объект.КодыУКТЗЕД Цикл
        Уник.Вставить(СтрокаКодов.КодУКТЗЕД, Истина);
    КонецЦикла;
    КоличествоТД = Объект.ДанныеДокументов.Количество();
    Результат = Цена × КоличествоТД;
    Если Уник.Количество() > 5 Тогда           // ❌ один раз на документ
        Результат = Результат + (Уник.Количество() − 5) × 0.2 × Цена;
    КонецЕсли;
    Возврат Результат;
КонецФункции

// ===== СТАЛО (per-ТД): каждой ТД свой штраф =====
Функция РассчитатьОформлениеТД(Объект, Цена) Экспорт
    Если Цена = 0 Тогда Возврат 0; КонецЕсли;

    ДопускТД = ПостроитьДопускТД(Объект);  // только активные статусы
    КодыПоТД = Новый Соответствие;

    Для Каждого КлючЗн Из ДопускТД Цикл
        КодыПоТД.Вставить(КлючЗн.Ключ, Новый Соответствие);
    КонецЦикла;

    Для Каждого СтрокаКодов Из Объект.КодыCMR Цикл
        НомерТД = СтрокаКодов.НомерДополнения;
        Если КодыПоТД[НомерТД] <> Неопределено И Не ПустаяСтрока(СтрокаКодов.КодТНВЭД) Тогда
            КодыПоТД[НомерТД].Вставить(СтрокаКодов.КодТНВЭД, Истина);
        КонецЕсли;
    КонецЦикла;

    Результат = Цена × ДопускТД.Количество();

    Для Каждого ЭлементТД Из КодыПоТД Цикл   // ✓ для каждой ТД
        Превышение = Макс(0, ЭлементТД.Значение.Количество() − 5);
        Результат = Результат + Превышение × 0.2 × Цена;
    КонецЦикла;

    Возврат Результат;
КонецФункции

§8 Что пока отсутствует и требует клиента

Phase 1.5 Ежедневный CSV-реестр от Владимира

Владимир присылает ежедневно CSV-файл «Реестр выпущенных ТД» (пример: 1-7 марто ЭТД (2).csv, 437 строк, 105 колонок, CP1251). Это внутренний реестр РТ — там все ТД с нашим участием и без.

Алгоритм сверки Владимира (3 шага):

  1. Ищем № ТД из обеспечения в колонке Регистрационный номер ТД → совпадение = Комплекс
  2. Не нашли по номеру? → ищем по Номера ТС + Декларант + Дата выпуска
  3. Не нашли вообще → ТолькоОбеспечение (ТД делал другой брокер или клиент сам)

Цитата Владимира: «Изначально соответствие номера ТД из обеспечения с номером из этой таблицы. Если всё ок, то проблемы нет. Если нет, то те, что не удалось идентифицировать — уже по номеру авто и остальным графам».

Phase 3 Прямая автозагрузка из Sigma PISrv

Сейчас EPF «APIСигма» загружает только ДДП-поручительства (ModuleId=999000 через REST API edapi.sigma-soft.ru/getreportggi). Сами ТД доступны только через бинарный протокол PISrv — уже обратно разобран (docs/pisrv-protocol.md), 972 записи R.048 выгружены скриптом data/pisrv_get_all_td.py.

Ограничения сервера: 10-15 сек между запросами, макс 10-15 SQL/сессию, работа только ночью (после инцидента 2026-04-08). Пока фазы 1-1.5 достаточно CSV-реестра.

§9 Как это будет работать — пошаговый сценарий для людей

Секция описывает путь двух источников данных через 1С: ДДП из API Сигмы, ТД из CSV Владимира — и как они сходятся в документе ОперацияПоПоручительству с per-ТД классификацией в ТЧ ДанныеДокументов. Все цифры — из живой InfoBase5 (MCP порт 6003, 23.04.2026).

TL;DR в одном предложении

У нас два источника данных, и оба пишут в документ ОперацияПоПоручительству: API Сигмы грузит ДДП (то, за что мы получили деньги), CSV Владимира грузит ТД (сами декларации). Сопоставление делается построчно в ТЧ ДанныеДокументов: если у ТД есть пара-ДДП → строка помечается Комплекс; если ТД есть, а ДДП нет → ТолькоТД (создаётся новый документ); если ДДП есть, а ТД нет → ТолькоОбеспечение. Модуль исРасчет считает каждую строку по её ТипУчета.

Тип документа один (ОперацияПоПоручительству), но в шапке появляется реквизит ВидОперации с двумя значениями: 🌐 ДДП-авто (автозагрузка из Сигмы — то что сейчас делает «Чтение деклараций» / EPF APIСигма) и 📑 ТД-файл (ручная загрузка реестра ТД Владимира через новую обработку). Это позволяет в журнале фильтровать и сразу видеть откуда документ пришёл.

Два источника данных — как они работают сегодня

ПОТОК 1

ДДП (поручительства) — API Сигмы

Источник: edapi.sigma-soft.ru/api/v1/report/getreportggi (REST, HTTP GET)

Кто грузит: EPF APIСигма (ОбновитьОперации в АРМ)

Что именно приходит: поручительства ДДП (ModuleId=999000) — для каждого клиента, у которого Сигма-Софт нам является контрагентом

Автоматизация: ✅ ежедневно, без участия человека (при желании — по кнопке)

Ограничение: API не видит клиентов типа «ТолькоТД» (им мы обеспечение не даём → у Сигмы с нами на них договора нет → в выдачу не попадают)

ПОТОК 2

ТД (транзитные декларации) — CSV-файл Владимира

Источник: внутренний реестр РТ (пример: 1-7 марто ЭТД (2).csv, CP1251, 105 колонок)

Кто готовит: Владимир, вручную/полуавтоматом из своего источника

Куда пишется: в тот же документ ОперацияПоПоручительству — дозаполняет ТЧ ДанныеДокументов (НомерГТД, ТС, Декларант, Дата выпуска, Подразделение). Для ТолькоТД-клиентов создаёт новые документы

Автоматизация: ❌ вручную (Phase 1). В Phase 3 возможна прямая загрузка через Sigma PISrv (сейчас на паузе после инцидента 2026-04-08)

Преимущество: видит всех клиентов, включая ТолькоТД (которых API не отдаёт)

В чём сейчас проблема

ТолькоТД-клиентов в системе сейчас 0. Их документов в базе нет вообще — API Сигмы их не отдаёт, а ручная загрузка ТД из CSV пока не реализована. При этом Владимир видит эти ТД в своём реестре ежедневно: мы везём декларации, но обеспечение даёт другой брокер → нам «платят только за ТД».

В существующих 1572 документах ТЧ ДанныеДокументов содержит 1868 строк, из которых 1864 (99.8%) имеют пустой ТипУчета. Модуль исРасчет при пустом значении уходит в fallback на реквизит контрагента, а он заполнен только у 3 из 2068 контрагентов — итого почти весь расчёт идёт по умолчанию как Комплекс.

Что оказалось неожиданным

Я изначально думал, что «Подразделение» = признак типа учёта (ЦО→Комплекс, ТрейдСолюшнс→ТолькоТД, ТАРГА→ТолькоОбеспечение). Это неверно. По реальному CSV:

ПодразделениеВсего ТДС «Номер ДДП ТД»Без
Центральный офис3523457
Трейд Солюшнс132132 (все!)0
ТАРГА101

Вывод: Подразделение — это наш внутренний отдел РТ (кто из сотрудников-специалистов вёл эту ТД), а не тип клиента. Все три подразделения могут вести и Комплекс, и ТолькоТД — определяется только наличием ДДП-номера. Колонку «Подразделение» сохраняем в ТЧ как справочный атрибут для группировки в отчётах.

Как это меняется для бухгалтера

Никак. Бухгалтер продолжает работать в АРМ как и раньше: выбирает период → загружает операции → жмёт Рассчитать. Единственная разница — сумма теперь правильная (в т.ч. появились ранее отсутствовавшие документы ТолькоТД-клиентов). Никаких новых кнопок, никакого обучения.

Как это меняется для Владимира

День 1 (первая массовая загрузка исторического CSV — по аналогии с присланным файлом 08.04.2026, 485 ТД за ~6 дней):

  1. Владимир экспортирует ЭТД-журнал за 4–6 недель (покрыть период существующих документов)
  2. Обработка раскладывает по 3 ведрам: ~2000 строк → Комплекс (обогащение существующих), ~30-50 строк → новые ТолькоТД, ~50-100 строк существующих → ТолькоОбеспечение
  3. Просматривает «ТолькоОбеспечение» (там могут быть сюрпризы), применяет
  4. Итог: все ДанныеДокументов получили Рег.№ТД, Подразделение, КолКодовТНВЭД. В базе появились новые ОПП типа ТолькоТД. АРМ → Рассчитать пересчитывает суммы правильно с учётом Schema 4

День N (ежедневная рутина, ~3 минуты):

  1. Утром экспортирует свежий ЭТД-журнал за сутки (~80 строк)
  2. Открывает обработку → «Прочитать CSV» → 3 вкладки с маленькими числами
  3. Быстрая проверка «Новые ТолькоТД» (0–3 строки), применяет
  4. Бухгалтер жмёт Рассчитать в АРМ — всё актуально

Различение видов операции в журнале документов

В 1С-типовых документах (Реализация, Поступление и т.д.) вариант контекста создания хранится в реквизите шапки «Вид операции» — один тип документа, но для пользователя визуально различимые записи. Применяем тот же паттерн, с двумя значениями:

Миграция существующих 1572 документов

Один раз при первом развёртывании: у всех существующих документов проставляется ВидОперации = ДДПАвто. Это корректно, потому что все они были созданы через «Чтение деклараций» / APIСигма — ни один документ ТолькоТД-клиента в базу ещё не попадал (0 в статистике). Документы с ВидОперации = ТДФайл появятся только после первого запуска Владимиром новой обработки «Загрузка реестра ТД».

Технически: при установке расширения хук ОбновлениеИнформационнойБазы выполняет UPDATE Документ.ОперацияПоПоручительству SET ВидОперации = &ДДПАвто WHERE ВидОперации IS NULL. Занимает ~1-2 сек на базу.

В ТЧ КодыCMR документа ОперацияПоПоручительству

Добавляем реквизит КодТНВЭД (Строка 10). В ТЧ обработок АРМ/ЧтениеДеклараций он уже есть — переносим на сам документ, чтобы Schema 4 считал штраф за коды per-ТД, а не суммарно.

Опционально: реквизит Контрагенты.ТипУчета как fallback

Обработка может одновременно «обучать» реквизит на справочнике: если у клиента все строки получили один и тот же ТипУчета — выставить его и на карточку контрагента. Это нужно только для ручно созданных новых документов, где нет CSV-строки — тогда сработает fallback (стр. 41-48 исРасчет). Для документов из API+CSV это не нужно, у них уже есть per-row ТипУчета.
