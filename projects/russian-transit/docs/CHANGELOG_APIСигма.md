## v2.11 — ТЗ-аккумуляция вместо `Объект.Декларация.Добавить()` (2026-05-12)

**Симптом.** Пользователь запустил v2.10 на 12 дней (01-12.04), прогон шёл **>1 часа** без видимого прогресса. UI 1С полностью заблокирован, сообщения не показываются, нельзя работать в конфигураторе.

**Корень (открыт deep-researcher'ом).** `Объект.Декларация.Добавить()` в цикле парсинга — узкое место. На каждый `.Добавить()` платформа **синхронизирует ВСЮ коллекцию реквизита формы клиент↔сервер**. При тысячах строк × 60 страниц = десятки тысяч RPC-синхронизаций. Замена на накопление в локальной `ТаблицаЗначений` + один финальный `Объект.Декларация.Загрузить(ТЗ)` даёт **~6× ускорения парсинга** ([forum.infostart 45134](https://forum.infostart.ru/forum9/topic45134/)).

Дополнительно зафиксировано: сервер Сигмы сейчас тупит (P3 в моём прямом замере = 65 сек, у других страниц 30-50 сек). При 30 страницах = ~25 мин только API.

**Фикс v2.11.**

1. **`ПолучитьОтчетПоДополнениям`** теперь создаёт `ТЗДекларация = Объект.Декларация.Выгрузить()` (с такой же схемой колонок и типами) перед циклом страниц
2. **`ЗаполнитьТабличнуюЧастьИзCSV`** принимает третий параметр `ТЗДекларация` и пишет туда вместо `Объект.Декларация.Добавить()`
3. **После цикла страниц** — один вызов `Объект.Декларация.Загрузить(ТЗДекларация)` (один RPC вместо тысяч)
4. **Обратная совместимость**: если функция вызвана без ТЗ — создаёт локально, в конце сохраняет в объект (`ЛегасиРежим`)

**Ожидаемый эффект.** Парсинг 12 дней (~30 страниц):
- v2.10: ~1+ часа (UI blocked × тысячи RPC)
- v2.11: ~15-25 минут (API + локальное накопление в ТЗ)

UI всё ещё блокируется (синхронный режим формы) — это решается отдельно через БСП.ДлительныеОперации в **v2.12**.

**Файлы.** `Module.bsl:367-490` — `ПолучитьОтчетПоДополнениям` с ТЗ, передача параметром. `Module.bsl:493-887` — `ЗаполнитьТабличнуюЧастьИзCSV(Данные, Кеши, ТЗДекларация)`, замена `Объект.Декларация.Добавить()` на `ТЗДекларация.Добавить()`, в конце `Загрузить(ТЗ)` в legacy-режиме.

**EPF.** `build/APIСигма_v2.11.epf` — 42527 байт
**Marker.** `SS-API-fix #13 v2.11`

## v2.10 — fix регрессии v2.9: глобальные lazy-кеши (2026-05-12)

**Симптом.** Пользователь запустил v2.9 на 12 дней (01-12.04, окно 18.03-26.04, ~30 страниц API), прогон работал **почти час** без результата. Это в 2-3 раза медленнее чем v2.6/v2.8.

**Корень (архитектурный).** В v2.9 кеши и batch-предзагрузка были помещены **внутрь `ЗаполнитьТабличнуюЧастьИзCSV`**. А эта функция вызывается **на каждой странице API** в цикле `ПолучитьОтчетПоДополнениям`. Получилось:
- Первый проход CSV для сбора уникальных — **дублирует парсинг каждой страницы** (×2 работа парсера)
- 10 batch-запросов на каждой странице — **×60 страниц = 600 SQL вместо 10**
- Кеши локальные внутри функции — между страницами не переиспользуются, на каждой странице с нуля

batch-запросы `... ГДЕ Наименование В (&Имена)` с 100-300 значениями в IN-списке на справочниках с 15k+ записями работают медленно (часто full-scan когда планировщик не уверен).

**Фикс v2.10.**

1. **Кеши вынесены в `ПолучитьОтчетПоДополнениям` через `Структура`** — инициализируются ОДИН РАЗ перед циклом страниц, передаются параметром в `ЗаполнитьТабличнуюЧастьИзCSV(ДанныеCSV, Кеши)`:
   ```bsl
   Кеши = Новый Структура;
   Кеши.Вставить("Валют", Новый Соответствие);
   Кеши.Вставить("Принципалов", Новый Соответствие);
   ... (11 кешей)
   ```

2. **Убран первый проход CSV** — он только дублировал работу
3. **Убраны batch-запросы** — оказались дороже на N страницах. Lazy-кэш через `КешНайтиПо*` достаточен:
   - Первое обращение → SQL + кэшируем (включая пустой результат)
   - Все последующие → O(1) из `Соответствие`
4. **МапаПодразделений теперь lazy** — на первом обращении один SQL, кэшируется. Повторные обращения через все страницы — O(1).
5. **Helper `ПостроитьКеш*ы` остались в коде** — на будущее, не вызываются.

**Ожидаемый эффект.** Парсинг каждой страницы:
- v2.6: ~30k строк × ~10 SQL = ~300k SQL за прогон 60 страниц
- v2.9: парсинг × 2 + 60 батч-запросов на справочниках 15k+ записей = деградация в 3×
- v2.10: ~30k строк × 1 SQL (по уникальным значениям, обычно <500 SQL на справочник за прогон). Всего ~5000 SQL.

Должно вернуть скорость v2.6 + добавить ускорение от кеша.

**Файлы.** `Module.bsl:367-461` — кеши в `ПолучитьОтчетПоДополнениям`, передача параметром. `Module.bsl:460+` — `ЗаполнитьТабличнуюЧастьИзCSV(ДанныеCSV, Кеши = Неопределено)`. Удалён блок первого прохода + batch. `ВернутьКонтрагента` — lazy кэш подразделений с явным записыванием пустых результатов.

**EPF.** `build/APIСигма_v2.10.epf` — 41972 байта (немного меньше v2.9 за счёт удаления первого прохода)
**Marker.** `SS-API-fix #12 v2.10`

## v2.9 — batch-предзагрузка справочников (2026-05-12)

**Симптом.** На «1 день» (15 дней API окно) парсинг тянулся в районе 10+ минут даже после v2.6 (O(N) счёт кавычек). Узкое место — `НайтиПоНаименованию`/`НайтиПоКоду` на каждой строке CSV.

**Измерение.** На реальном прогоне 01.04 (~2400 операций) в основном цикле парсинга выполнялось:

| Справочник | Вызовов на строку | Всего SQL |
|---|---|---|
| Валюты | 1 | 2400 |
| Принципалы | 1 | 2400 |
| Контрагенты (для Декларанта) | 1-3 | 2400-7200 |
| Декларанты | 0-1 | до 2400 |
| Перевозчики | 1 | 2400 |
| ТранспортныеСредства (Осн+Доп) | 1-2 | до 4800 |
| ТаможенныеПункты (НайтиПоКоду × 4 + НайтиПоНаименованию × 2) | 4-6 | до 14400 |
| Пользователи | 1 | 2400 |
| `ВернутьКонтрагента` шаг 1 (email из КИ) | 1 | 2400 |
| `ВернутьКонтрагента` шаг 2 (подразделение РС) | 1 | 2400 |
| **Итого** | | **~30000-45000 SQL** |

При среднем ~3-5 мс на SQL — это **1.5-3.5 минуты** только на поиск в справочниках.

**Фикс.** Двухпроходная архитектура:

1. **Первый проход** по `МассивПолныхСтрок` — собирает уникальные значения по индексам [1] Валюта, [4] Принципал, [14] Декларант/Контрагент, [18] Перевозчик, [22] коды ТС, [25]/[28] коды ТамПунктов, [26]/[29] наим ТамПунктов, [87] Пользователь, [96] Подразделение Сигмы. Через `Соответствие` (дедуп по ключу).

2. **Batch-запросы** через новые helper-функции:
   - `ПостроитьКешПоНаименованию(Кеш, ИмяТаблицы, СписокИмён)` — один SQL `... ГДЕ Наименование В (&Имена)`
   - `ПостроитьКешПоКоду(Кеш, ИмяТаблицы, СписокКодов)` — один SQL по кодам
   - `ПостроитьМапуПодразделенийКонтрагентов(СписокПодразделений)` — копия логики из ЗагрузкаРееструТД

3. **В основном цикле** все `Справочники.X.НайтиПо*` заменены на `КешНайтиПо*(Кеш, Менеджер, Значение)`. Кэш-обёртка возвращает из Соответствие если есть, иначе делает обычный поиск + кэширует.

4. **После автосоздания** (`СоздатьПринципала`, `СоздатьДекларанта`, `СоздатьПеревозчика`, `СоздатьЭлемент → Записать` для ТС/Пользователя) — результат добавляется в кеш чтобы повторная встреча того же имени дала O(1).

5. **`ВернутьКонтрагента`** расширена опциональными параметрами `МапаПодразделений` и `КешEmail`:
   - `МапаПодразделений` — batch-предзагружена один раз, lookup O(1) вместо SQL запроса в РС
   - `КешEmail` — lazy memoization (на 2000 строк уникальных email десятки, не тысячи)

**Ожидаемое ускорение.** При типичном разнообразии:
- Валюты: 5-10 уникальных вместо 2400 SQL → 99.8% реквизитов из кэша
- Перевозчики/Декларанты: ~100-300 уникальных вместо 2400-7200 → 95% из кэша
- ТамПункты: ~50 уникальных вместо 14400 → 99.7% из кэша
- Подразделения: ~50 вместо 2400 → 98% из кэша

Должно дать **~1-2 минуты экономии** на 1 день. После v2.6 (O(N) парсер) + v2.9 (кеш) полный прогон «1 день» оценочно: API ~10 мин + парсинг 1-2 мин + создание документов 1-2 мин = **~13-14 минут** против изначальных 30+.

**Файлы.**
- `Module.bsl`: новая `#Область КешСправочников` (helper-функции), правки в `ЗаполнитьТабличнуюЧастьИзCSV` (первый проход + batch + замены в цикле), расширена сигнатура `ВернутьКонтрагента`
- Файл вырос с 1980 до 2128 строк

**EPF.** `build/APIСигма_v2.9.epf` — 42179 байт
**Marker.** `SS-API-fix #11 v2.9`

## v2.8 — Контрагент попадает в шапку Документа (2026-05-12)

**Симптом.** После прогона 01.04.2026 ни в одном из 270 документов не заполнен `Документ.ОПП.Контрагент`, при этом в API есть и email в комментарии (`#hvoev@tbroker...`), и подразделение Сигмы. В журнале документов у некоторых стояло обрезанное «ТРАНЗИТНЫЙ» как Контрагент — случайно прошло потому что обрезка до 10 символов вкладывалась в имя.

**Корень.** Тот же type-mismatch паттерн что в v2.5 для ТС:
- `ТЧ.Декларация.Контрагент = xs:string(10)` — присвоение ссылки обрезает её до 10 символов (фактически — ломает данные)
- `Документ.ОПП.Контрагент = СправочникСсылка.Контрагенты`
- `ЗаполнитьЗначенияСвойств(Док, Строка)` молча игнорирует копирование

При этом сам **поиск контрагента работает корректно** через `ВернутьКонтрагента(Представление, ПодразделениеСигма)` (Module.bsl 951-1004): email из комментария → КИ контрагентов/партнёров (шаг 1), `[96] uso_name` → РС `СоответствияПодразделенийКонтрагентам` (шаг 2). Результат поиска получается, но обрезается при присвоении в ТЧ.

В v2.5 я добавил fallback-блоки для ТС, Валюты, Организации, Ответственного, но **не добавил для Контрагента** — неверно понял исходную политику «работники заводят сами» как «не заполнять никогда», хотя это означало «не АВТОСОЗДАВАТЬ» (поиск разрешён).

**Фикс.** Изменён тип реквизита `Декларация.Контрагент` в XML обработки:
```xml
<!-- было -->
<Type>
    <v8:Type>xs:string</v8:Type>
    <v8:StringQualifiers>
        <v8:Length>10</v8:Length>
        <v8:AllowedLength>Variable</v8:AllowedLength>
    </v8:StringQualifiers>
</Type>

<!-- стало -->
<Type>
    <v8:TypeSet>cfg:CatalogRef</v8:TypeSet>
</Type>
```

После этого:
- Поиск `НоваяСтрока.Контрагент = ВернутьКонтрагента(...)` сохраняет ссылку как ссылку (не обрезает)
- `ЗаполнитьЗначенияСвойств(Док, Строка)` копирует Контрагент в шапку (типы совместимы)
- Никакого fallback-блока не нужно — стандартный механизм платформы работает

**Политика подтверждена и зафиксирована в SPEC.md §3.3:**
- ✅ Поиск по email + подразделению — **есть** (работал с самого начала)
- ❌ Автосоздание контрагентов — **нет** (работники заводят вручную, риск кривых наименований)
- ❌ Поиск по ИНН — **нет** (это `ЗагрузкаРееструТД`, другая сущность с CSV ЭТД)

**Файлы.**
- `apisigma_dump_FROM_BUILD/APIСигма.xml:266-282` — изменение типа реквизита
- `docs/specs/APIСигма-SPEC.md` — новый документ ТЗ (200+ строк)

## v2.6 — O(N²) → O(N) в парсере CSV (2026-05-12)

**Симптом.** Пользователь поставил «1 день» (01.04.2026), прогон тянулся **> 30 минут**.

**Корень.** Module.bsl 482-487 — посимвольный счёт кавычек через `Сред()`/`СтрДлина()`:
```bsl
КоличествоКавычек = 0;
Для Сч = 1 По СтрДлина(ТекущаяСтрока) Цикл
    Если Сред(ТекущаяСтрока, Сч, 1) = Символ(34) Тогда
        КоличествоКавычек = КоличествоКавычек + 1;
    КонецЕсли;
КонецЦикла;
```
При склейке многострочных полей `ТекущаяСтрока` накапливается, счёт ПЕРЕСЧИТЫВАЕТСЯ заново — фактически O(N²). Для 368k строк × ~1000 символов (замеры: 21 страница × 99 МБ за окно 18.03—01.04) это десятки минут CPU-time.

**Замер размера данных (прямой POST к Сигме):**
- API окно 18.03—01.04 (15 дней буфер для НачальнаяДата=01.04): 21 страница, 368 152 строки CSV, 99.25 МБ
- 637 секунд (~10.6 мин) только на API-запросы (~30 сек/страница)

**Фикс.** `СтрЧислоВхождений` (нативный C++ платформы) + накопительный счёт (считаем только по новому куску при склейке):
```bsl
Если ТекущаяСтрока = "" Тогда
    ТекущаяСтрока = Стр;
    КоличествоКавычек = СтрЧислоВхождений(Стр, Символ(34));
Иначе
    ТекущаяСтрока = ТекущаяСтрока + " " + Стр;
    КоличествоКавычек = КоличествоКавычек + СтрЧислоВхождений(Стр, Символ(34));
КонецЕсли;
```

**Файлы.** `Module.bsl:472-489` (функция `ЗаполнитьТабличнуюЧастьИзCSV`)
**EPF.** `build/APIСигма_v2.6.epf` — 39165 байт

## v2.5 — fix полной шапки документа ОПП (2026-05-11)

**Симптом.** После прогона 30.04.2026 все 32 документа ОПП созданы **без `ОсновноеТС/ДополнительноеТС`**. Изначально полагали что у части `ДополнительноеТС` заполнено — фактически НЕТ (брутальная честность): SQL `СУММА(ВЫБОР КОГДА ДополнительноеТС = ПустаяСсылка ТОГДА 1...)` = 32 из 32.

**Гипотезы (проверены через MCP execute_query + execute_code):**
- H1. API не возвращает [22] → **отпала.** Прямой POST к Сигме: `[22] = "30BM681/30ZA261"` присутствует
- H2. Уникальность кода ТС блокирует автосоздание → **отпала.** Журнал регистрации за сутки: 0 новых ТС, 0 исключений
- H3. **Type mismatch ZSV** → ✅ подтверждена
- H4. ПередЗаписью обнуляет → **отпала.** Прямое присвоение `Док.ОсновноеТС = Ссылка` + `Записать()` в транзакции с откатом — сохраняется

**Корень (доказан).** В ТЧ Декларация обработки 8 строковых полей имеют тип `xs:string(10)`, а в шапке `Документ.ОперацияПоПоручительству` — ссылочные:

| Контрагент | String(10) | СправочникСсылка.Контрагенты | ❌ by design не трогаем |
| ВалютаДокумента | String(10) | СправочникСсылка.Валюты | ❌ нужен fallback |
| Организация | String(10) | СправочникСсылка.Организации | ❌ нужен fallback |

Плюс legacy опечатка в имени реквизита: `СрокИспользованияДополнения` в ТЧ vs `CрокИспользованияДополнения` в шапке (латинская `C` в шапке) — `ЗаполнитьЗначенияСвойств` не копирует.

**Фиксы (4 шт).**
1. **SS-API-fix #4** — в обоих `Попытках` автосоздания ТС (572-588) добавлен `ЗаписьЖурналаРегистрации` в `Исключение` (раньше глушилось молча — 0 видимых ошибок, и при этом 0 созданных ТС)
2. **SS-API-fix #4 (часть 2)** — в fallback `СоздатьДокументыНаСервере` (1393-1407, 1414-1428) добавлено автосоздание ТС если `НайтиПоКоду` промахнулся
3. **SS-API-fix #5** — новые fallback для `ВалютаДокумента`, `Организация`, `Ответственный` (заполняется `Пользователи.ТекущийПользователь()`), `CрокИспользованияДополнения` (с латинской C)
4. **SS-API-fix #6** — лог состояния `Док.ОсновноеТС/ДопТС/ВалютаОбеспечения/Декларант/Перевозчик/Принципал` перед `Док.Записать()`. Событие `APIСигма.СостояниеДокПередЗаписью` (Информация). На каждый Док — 1 запись после прогона.

**Бизнес-решения зафиксированы:**
- **Контрагент НЕ автосоздаём** — работники заполняют вручную, чтобы избежать кривых наименований. ZSV не копирует благодаря несовместимости типов — защищено
- **ZSV перезатирание оставшихся CatalogRef-полей** (Декларант/Перевозчик/Принципал/Пункт*) — текущее поведение **не меняли**. При повторном прогоне может затереть ручную правку. Если защищать — отдельная задача
- **`Док.ДанныеДокументов.Очистить()` + 1 строка из шапки** — поведение Задачи 4 от 10.04, **не трогали**. При повторном прогоне ручные правки ДД теряются
