# APIСигма — ТЗ обработки импорта операций из Сигма-Софт

> Спецификация. Что должно работать. Обновляется при каждом изменении логики (вместе с CHANGELOG_APIСигма.md).

**Источник:** `projects/russian-transit/epf/APIСигма/APIСигма/Forms/Форма/Ext/Form/Module.bsl`
**Бэкенд:** `https://edapi.sigma-soft.ru/api/v1/report/getreportggi`
**Тип файла:** EPF (внешняя обработка)
**Связь с конфигурацией:** заполняет `Документ.ОперацияПоПоручительству` (объект из CFE «Русский_Транзит»)

---

## 1. Контракт API Сигмы

**Endpoint:** `POST /api/v1/report/getreportggi?participantcode=<код>`
**Auth:** `Bearer <JWT>` в заголовке. JWT живёт ~30 мин — нужна ре-авторизация при 401 на любой странице (max 3 ретрая за прогон).
**Body:**
```json
{"datebegin": "yyyy-MM-dd", "dateend": "yyyy-MM-dd", "withgoods": 1, "pagenum": N, "quantity": 200}
```

**Ответ:**
```json
{"resCode": 0, "resData": "<CSV-строка>", "resDescription": "..."}
```
`resData` — CSV с `;` разделителем, 114 колонок, заголовок в первой строке.

**Ограничения:**
- `quantity` max 200 (более — 500 ошибка)
- `withgoods=0` — 500 ошибка (отключить нельзя)
- Сервер отдаёт ~30 сек/страница (часто), увеличение нагрузки даёт 60+ сек
- Пагинация: пустой `resData` = конец данных

## 2. Семантика дат

| Поле API | Индекс | Смысл |
|---|---|---|
| `BDT_DATECRT` | [52] | Дата **создания** записи в Сигме (по этому полю фильтрует API через `datebegin/dateend`) |
| `TRANSITOPENDATE` | [60] | Дата **выпуска** ТД (она же = дата документа ОПП в 1С) |
| `BDT_DATEMOD` | [53] | Дата последнего изменения в Сигме |
| `MSS_CREATEDATE` | [68] | Дата создания сессии в Сигме |
| `TRANSITFACTENDDATE` | [62] | Дата фактического завершения транзита |
| `DAYS_FROM_TRANSITOPENDATE` | [93] | Сколько дней прошло с выпуска (сервер считает) |

**Буфер `-N дней` к `НачальнаяДата`:** API фильтрует по `BDT_DATECRT`, но нам нужен `TRANSITOPENDATE`. Между этими датами есть разрыв (запись создаётся в Сигме когда ТД готовится, выпуск может быть позже). По умолчанию буфер = **14 дней**, но требует подтверждения замером.

## 3. Сущности и логика заполнения

### 3.1 Документ.ОперацияПоПоручительству

**Создаётся** при условии: строка CSV имеет `GOODSNUMERIC[98] = "1"` ИЛИ (пустое И `СуммаОбеспечения[0] > 0`). Прочие строки — это товарные позиции к операции.

**Дедупликация:** по `НомерГТД`. При повторном прогоне документ найдётся и **обновится** (через `ЗаполнитьЗначенияСвойств`).

### 3.3 Контрагент — детальная логика (`ВернутьКонтрагента`)

**Вход:** `(Представление, ПодразделениеСигма)` где Представление = Комментарий из CSV `[84]`, ПодразделениеСигма = `[96] uso_name`.

**Шаг 1: Email из комментария.**
- Из Представления извлекается `email` через `ИзвлечьEmailИзРешёток` (формат `#user@domain.tld #...` или `#user@domain.tld`)
- `email` → точный поиск в `Справочник.Контрагенты.КонтактнаяИнформация` (Тип=Адрес электронной почты) И `Справочник.Партнеры.КонтактнаяИнформация` → `Контрагенты.Партнер`
- Найден → **возврат ссылки**

**Шаг 2: Подразделение.**
- ПодразделениеСигма → `РегистрСведений.СоответствияПодразделенийКонтрагентам` (поле `ПодразделениеСигма` = ключ, `Контрагент` = значение)
- Найден → **возврат ссылки**

**Шаг 3: Не нашли.**
- Запись в журнал `APIСигма.КонтрагентНеНайден` (Предупреждение) с диагностикой: email, подразделение, рекомендация
- Возврат `Справочники.Контрагенты.ПустаяСсылка()`

**Политика:**
- ❌ **НЕ автосоздаём** контрагентов из API. Работник заводит вручную (риск кривых наименований)
- ❌ **НЕ ищем по ИНН** — это другая сущность (`ЗагрузкаРееструТД`, не наша)
- ✅ Если контрагент не найден — документ создаётся с пустым Контрагентом, работник доводит руками

### 3.4 Принципал — отличается от Контрагента

- Автосоздаётся через `СоздатьПринципала(имя)` если не найден
- Источник: `[4]` (название организации поручителя)
- Это **прямое поведение по требованию** — список принципалов узкий и контролируется

### 3.5 Декларант — спец-логика

- Сначала `Справочники.Контрагенты.НайтиПоНаименованию([14])`. Если найден — это **контрагент** в роли декларанта.
- Иначе `Справочники.Декларанты.НайтиПоНаименованию([14])` — отдельный справочник декларантов.
- Если не нашёл нигде — `СоздатьДекларанта([14])` (автосоздаётся).
- Тип реквизита Документа: `Пользователь | Декларанты` (составной).

### 3.6 Перевозчик

- `Справочники.Перевозчики.НайтиПоНаименованию([18])`, иначе `СоздатьПеревозчика([18])` (автосоздание).
- Источник: `[18] MSL_TRANSPORTOPERATOR_ORGNAME`.

### 3.7 ТС — нормализация кода

- `[22] LICENSEPLATE` имеет формат `"<основное>/<доп>"` (например `"30BM681/30ZA261"`).
- В справочнике `ТранспортныеСредства` код хранится **без пробелов** (10 символов max).
- Нормализация: `СтрЗаменить(СокрЛП(...), " ", "")`.
- `НайтиПоКоду(нормализованный)`, иначе создать с `Код = нормализованный`, `Наименование = с пробелами`.

## 4. Этапы прогона

### 4.1 «Получить отчёт»

1. `ПолучитьОтчетПоДополнениям()` → цикл по страницам API
2. На каждой странице: HTTP POST → парсинг CSV → добавление строк в `Объект.Декларация`
3. Если 401 — `АутентификацияЭДСигма(КодДоступа)` → ретрай этой же страницы (v2.7: до 3 раз, на любой странице)
4. Конец: пустой `resData` или resCode≠0

**Фильтрация на нашей стороне:**
- `GOODSNUMERIC[98] = "1"` или пустой с суммой > 0 — это операция, добавляем
- Пост-фильтр по `TRANSITOPENDATE[60]` в окне `НачальнаяДата..КонечнаяДата` (отбрасываем строки с `BDT_DATECRT` в буфере, но `TRANSITOPENDATE` уже вне окна)

### 4.2 «Создать документы»

ЭТАП 1: для каждой строки `Объект.Декларация`:
1. Поиск дока по `НомерГТД` → найден = обновляем, нет = создаём новый
2. `ЗаполнитьЗначенияСвойств(Док, Строка)` копирует совпадающие по типу поля
3. Fallback-блоки для несовместимых типов (см. таблицу 3.2)
4. `Док.КодыCMR.Очистить()` + добавление CMR из `Объект.КодыCMR` по соответствию
5. `Док.ДанныеДокументов.Очистить()` + одна строка из шапки
6. `Док.Дата = TRANSITOPENDATE` (или ДатаОформления)
7. Логи в ЖР: `APIСигма.СостояниеДокПередЗаписью` (одна запись на документ)
8. `Док.Записать()` — Попытка ловит ошибки и инкрементит `СчётчикОшибок`

ЭТАП 2: «Сгруппировать» — отдельная кнопка. Группирует документы с одинаковым `ТС + Контрагент + Дата` в один (доноры удаляются ПометкойУдаления).

### 4.3 «Удалить документы за период»

`Док.Удалить()` (непосредственное физическое удаление) для всех документов с `Дата МЕЖДУ &Нач И &Кон`. Логирует «Удалено: N, ошибок: M».

## 6. Известные ограничения

- **Объём данных:** «1 день» в форме → API окно 15 дней → ~20 страниц × 30 сек = ~10 минут API + парсинг. Это нижний предел.
- **JWT 30 мин:** длинные прогоны (60+ страниц) спасает re-auth v2.7.
- **`НайтиПоНаименованию` на каждую строку CSV:** потенциально 5+ тыс. SQL запросов на 1000 операций. Кэширование пока не реализовано (TODO для будущей версии).
- **`Док.ДанныеДокументов.Очистить()` при каждом прогоне** — теряет ручные правки ДД у уже существующих документов. Поведение существующее, в SPEC зафиксировано.

| **Контактные данные документа (Контрагент/Принципал/etc.) при повторном прогоне** | — | — | **ZSV перезатирает** совпадающие по типу поля. Ручная правка теряется. Если защищать — отдельная задача. |
