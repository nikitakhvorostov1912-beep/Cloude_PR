# Архитектурные стандарты 1С

> Источник: comol/ai_rules_1c dev-standards-architecture.md (адаптировано).
> Используется агентами: 1c-code-architect, 1c-arch-reviewer, 1c-code-writer.

## 1. Архитектурные паттерны

### Где живёт бизнес-логика
- Бизнес-логика — **только в общих модулях**, не в модулях форм
- Модули форм — только UI-логика и вызовы общих модулей
- Имена серверных модулей — суффикс `Сервер` или `СерверПовтИсп`
- Имена клиентских модулей — суффикс `Клиент`

### Result-Structure паттерн
Для возврата составных результатов — явная структура:
```bsl
Функция ПроверитьДанные(Параметры) Экспорт
    Результат = Новый Структура;
    Результат.Вставить("Успех", Истина);
    Результат.Вставить("Ошибки", Новый Массив);
    Результат.Вставить("Данные", Неопределено);
    
    // логика проверки...
    
    Возврат Результат;
КонецФункции
```

### Early Return паттерн
```bsl
// ПЛОХО: глубокая вложенность
Если Условие1 Тогда
    Если Условие2 Тогда
        // логика

// ХОРОШО: ранний выход
Если НЕ Условие1 Тогда Возврат; КонецЕсли;
Если НЕ Условие2 Тогда Возврат; КонецЕсли;
// логика
```

### Поиск по Соответствию (O(1))
```bsl
// ПЛОХО: O(n) поиск
СтрокаТЧ = Документ.Товары.Найти(НоменклатураСсылка, "Номенклатура");

// ХОРОШО: O(1) через Соответствие (строить ДО цикла)
ИндексТЧ = Новый Соответствие;
Для Каждого Строка Из Документ.Товары Цикл
    ИндексТЧ.Вставить(Строка.Номенклатура, Строка);
КонецЦикла;
СтрокаТЧ = ИндексТЧ.Получить(НоменклатураСсылка);
```

## 2. Расширения (CFE) — правила размещения

- Предпочитать **подписки на события** перед прямыми модификациями типового кода
- Новые объекты размещать согласно параметру `.dev.env → {NEW_OBJECTS_IN}`:
  - `main_configuration` — в основную конфигурацию
  - `extension` — в расширение
- Для Русского Транзита — всегда `extension` (CFE), папка `src/cfe/`

### Именование объектов расширения
- Все новые объекты — с префиксом `{PREFIX}` (для Русского Транзита = `РТ_` или `РусскийТранзит_`)
- Реквизиты типовых объектов — с префиксом
- Элементы форм на типовых формах — с префиксом
- Внутри нетиповых объектов (с префиксом) — БЕЗ префикса

## 3. Асинхронность и модальность

- Модальные диалоги (`ВопросПользователю`, `ПредупреждениеПользователю`) — **запрещены**
- Использовать `Асинх`/`Ждать` для:
  - Фоновых задач (ДлительныеОперации)
  - Запросов к внешним сервисам
  - Файловых операций
- Для 1С платформы < 8.3.18 — `ОписаниеОповещения`

## 4. Запрещённые конструкции

```bsl
// ЗАПРЕЩЕНО
Выполнить(ТекстПрограммы);          // произвольный код
Вычислить(Выражение);               // произвольные выражения
Пароль = "mysecret";               // хардкод учётных данных
ТекущаяДата();                     // использовать ТекущаяДатаСеанса()
?(Условие, Значение1, Значение2);   // тернарный оператор
```

## 5. Доступ к данным

### Запрещено: обращение через точку
```bsl
// ЗАПРЕЩЕНО — загружает весь объект
ИНН = Контрагент.ИНН;
Наименование = Документ.Организация.Наименование;
```

### Обязательно: SSL-методы
```bsl
// Один реквизит
ИНН = ОбщегоНазначения.ЗначениеРеквизитаОбъекта(Контрагент, "ИНН");

// Несколько реквизитов одного объекта
Реквизиты = ОбщегоНазначения.ЗначенияРеквизитовОбъекта(Контрагент, "ИНН, КПП");

// Несколько объектов, один реквизит
ИНН = ОбщегоНазначения.ЗначениеРеквизитаОбъектов(Контрагенты, "ИНН");

// Несколько объектов, несколько реквизитов
Реквизиты = ОбщегоНазначения.ЗначенияРеквизитовОбъектов(Контрагенты, "ИНН, КПП");
```

### Кеширование
```bsl
// Для повторяющихся значений в цикле — кеш через Соответствие ДО цикла
КешКурсов = Новый Соответствие;
Для Каждого Строка Из Таблица Цикл
    КурсВалюты = КешКурсов.Получить(Строка.Валюта);
    Если КурсВалюты = Неопределено Тогда
        КурсВалюты = ПолучитьКурс(Строка.Валюта, Дата);
        КешКурсов.Вставить(Строка.Валюта, КурсВалюты);
    КонецЕсли;
КонецЦикла;
```

## 6. Производительность

| Требование | Правило |
|-----------|---------|
| Серверные операции | Пакетные, не поострочные |
| Запросы | Никогда в цикле, использовать ВТ |
| Привилегированный режим | Минимально, только где необходимо |
| Кеширование | Для повторяющихся вычислений в цикле |
| Индексирование | Использовать индексированные поля в запросах |

## 7. Временные таблицы — соглашение по именованию

Префикс `ВТ_` обязателен:
```bsl
// В запросе
"ПОМЕСТИТЬ ВТ_ТоварыДляОтгрузки"
"ИЗ ВТ_ТоварыДляОтгрузки КАК ВТ_Товары"
```

## 8. Признаки проблемного кода (Code Smells)

| Запах | Признак | Рефакторинг |
|-------|---------|-------------|
| Сгусток данных | Одни и те же параметры передаются вместе | Объединить в Структуру |
| Примитивная одержимость | Строка вместо типизированного объекта | Создать тип/справочник |
| Расходящееся изменение | Одно изменение требует правок в N местах | Выделить общий модуль |
| Дробное изменение | Одна фича размазана по N модулям | Объединить логику |
| Зависть к функциям | Модуль А слишком много знает о модуле Б | Перенести логику в Б |
| Повторное использование переменной | Одна переменная для разных значений | Объявить отдельные |

## 9. Spec-Driven Development (для Средней / Сложной / Критичной)

Перед началом архитектурного проектирования — обязателен **spec.md** со статусом `approved`. Без spec не стартуем — иначе крутимся вокруг недоопределённого ТЗ (правило 3 итераций сработает в худшем варианте).

### Когда применять SDD

| Сложность | SDD обязательно? |
|-----------|-----------------|
| Простая (1 модуль, очевидно) | Нет, комментария коммита достаточно |
| Средняя (несколько модулей) | Да, мини-spec |
| Сложная (несколько подсистем) | Да, полный spec + plan |
| Критичная (архитектурные изменения) | Да, spec + plan + явный approval |

### Шаблон spec.md

```markdown
# Spec: <название фичи>
**Status:** draft | approved | done
**Owner:** <ник заказчика/PO>
**Date:** YYYY-MM-DD

## Problem
<1-3 предложения: какую боль закрываем>

## Out of scope
<что НЕ делаем — явный список>

## Acceptance criteria
<3-7 проверяемых пунктов: «при X — система делает Y»>

## Risks
<2-4 риска: дедлок, регрессия типового, RLS, производительность>
```

### Workflow

1. spec.md `draft` → обсуждение с заказчиком/архитектором
2. spec.md `approved` → переход к Discovery (`1c-feature-dev` Phase 1)
3. Архитектура (`1c-code-architect`) → план реализации
4. Реализация (`1c-code-writer` + `1c-tdd`) → vertical slices
5. spec.md `done` → итог в summary.md

### Связь с правилом 3 итераций

Если на этапе Discovery/Design AI требует > 3 раундов уточнений — STOP, вернуться к Spec и переформулировать. Подробнее: `rules/1c/1c-ai-collaboration.md`.

Полный workflow: скилл `1c-feature-dev` (Phase 0).
